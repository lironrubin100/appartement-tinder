# Public listing location: local preparation for D4

- Status: local migration draft and review plan; no hosted change. SL02.1 remains incomplete; SL03.1 is its dependent packet. D4 and `docs/specs/TECHNICAL_DEFAULTS.md` require a stable persisted point chosen with cryptographically secure randomness in a 300–700 metre annulus around the exact location; it must not be derived from a public identifier.
- Evidence, 20 October: `20261007000100_listing_location_privacy.sql` derives a fixed 500 metre displacement from `hashtextextended(id::text, 0)`. In isolated Docker, one synthetic `Local SL02 home` row was selected and its exact latitude and longitude reconstructed from the published coordinates and public ID to within 0.00000001 degrees. No real-user point was tested. The currently deployed transform is therefore not evidence of D4 privacy.
- Proposed local migration for review: generate one independent cryptographically random angle and distance for each existing valid property, store only the resulting approximate point in the already persisted `public_lat`/`public_lng` columns, and replace the insert/location-change trigger to generate a new point only when the property location is initially set or a reviewed location correction occurs. Ordinary edits and repeated reads must leave the point unchanged. Do not store or expose the random offset or seed, and do not provide a public endpoint exposing both old and new points.
- Migration review must account for cached or previously observed old coordinates: rotating cannot retract previously exposed information, and combining observations can narrow the location. Review existing data and rollout timing before a single coordinated change; never describe the replacement as anonymous or as undoing historical exposure. Preserve exact addresses, grants, legitimate inquiry history and synthetic demo fixtures.
- Local acceptance before any hosted action: seed synthetic edge and representative locations; assert distances in the approved annulus, stable repeated reads and normal edits, fresh randomness across synthetic properties sharing an exact location, location-correction behavior, non-inversion using the old public-ID algorithm, no exposed seed/offset or precise coordinates in public projections, and unchanged owner/accepted-inquiry authorization. Exercise ordinary authenticated clients and affected map/listing UI. Check rounding, longitude conversion at Israel's latitude extremes, failure rollback, migration repeatability and any existing location correction workflows. Synthetic tests cannot prove anonymity.
- Release boundary: SL02.1 explicitly says no hosted mutations; inspect packet and current owner/target/data/ownership policy before any later migration. Review the migration and complete applicable acceptance before integration, deployment, or a live rotation. Do not take this preparation as permission to change the shared database.
- Local implementation checkpoint: `20261020204057_private_random_listing_location.sql` uses independent cryptographically random UUID bits to generate an area-uniform annulus displacement, retains the point on unchanged coordinates and serializes writes during backfill with a table lock. It was applied only to disposable Docker after the ownership-function origin substitutions described in the SL02 handoff; the lock was added to the file afterward. A two-session local Postgres check confirmed that the lock blocks a competing no-op apartment update until timeout; it did not test the entire migration under concurrent publication. Twelve synthetic rows were in the approved distance range and none was reversed by the prior ID-derived formula. PGlite tests pass for distance, repeat stability, distinct synthetic points, helper denial, boundary latitudes and a synthetic correction. Five ordinary-client/browser tests passed against the local runtime, including range and owner/outsider public-point agreement. A read-only shared-target aggregate found 15 listings and no out-of-bound coordinates at that moment, and the live function still contains the old public-ID hash. This evidence does not establish anonymity, eliminate historic exposure or authorize live rotation.
- Additional two-session local test held the proposed lock while calling `publish_apartment` as the synthetic owner with actual owner-uploaded photos. The call reached the apartment insert and timed out on that lock; the lock transaction rolled back and no test publication was committed. This confirms the RPC's write is serialized by the chosen lock, but is not a complete migration-under-load or post-lock publication test.
- Live update, 20 October: owner explicitly approved the hosted database update and existing public-point rotation. Applied `private_random_listing_location` to project `npbduvjnqnbydolmdpsc` as migration `20261020204057`, and renamed the repository file to match the recorded live version. Read-only verification found all 15 listings within 300–700 metres, no missing public points, the new random trigger active, and execution of the random-point helper denied to anon and authenticated. Previous observations of old public points cannot be retracted. Local synthetic ordinary-client, database and browser checks precede this change; production user-journey acceptance has not yet been established. Security advisor reports existing project findings requiring separate investigation; no claim is made that the full project is secure.
