# Chat MVP implementation plan

## Product boundary

- A direct chat opens only when the recipient accepts a Like.
- MVP supports text messages, unread counts and realtime delivery inside an open thread.
- Group chats, apartment enquiry chats, listing-card messages, attachments and notifications are deferred.

## Delivery order

1. **Database foundation — complete in code**
   - `accept_like` remains the atomic conversation-creation entry point.
   - Conversations cache the newest message preview for Inbox reads.
   - `list_chat_inbox()` returns only the caller's direct conversations, with the other participant and unread count.
2. **Chat UI — complete in code**
   - `/chats` reads the Inbox RPC.
   - `/chats/[conversationId]` checks membership through the Inbox RPC, loads message history and sends text messages.
   - Opening a thread moves the caller's `last_read_at` marker.
3. **Realtime — complete in code**
   - Subscribe only while a conversation thread is open.
   - The database migration adds `messages` to Supabase Realtime's Postgres publication.
4. **Apply and verify — next**
   - Apply `20261013000100_chat_inbox_foundation.sql` to the connected Supabase project.
   - Verify the Like → accept → Inbox → send → receive flow with two users.
   - Verify RLS: an unrelated user cannot list or insert messages in the conversation.
5. **Testing setup — after the core flow is verified**
   - Use two persistent test users in separate browser profiles.
   - Keep any password/test-login mechanism development-only; do not expose service-role credentials to the browser.

## Authentication session fix

The Google callback must return the same response object on which
`exchangeCodeForSession` sets cookies. The callback implementation now does
this. Confirm in the browser that its response has `Set-Cookie`, then refresh
and reopen the app using the same origin (do not alternate localhost and
127.0.0.1).
